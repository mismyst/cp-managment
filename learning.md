## 1. What SCD Type 2 does

SCD means **Slowly Changing Dimension**. Type 2 preserves a row’s history: when a tracked attribute changes, the old version is marked as expired and a new version is inserted. The old values remain available for historical reporting.

For example, if source record `CP-10` changes its name:

| Surrogate key | Source/business ID | Name | Effective start | Effective end | Active? |
|---:|---|---|---|---|---|
| 101 | CP-10 | Old name | 2026-01-01 | 2026-03-10 | No |
| 205 | CP-10 | New name | 2026-03-10 | 9999-12-31 | Yes |

The source/business ID stays the same. The **surrogate key** changes because each version is a separate dimension row.

## 2. Columns typically needed for SCD2

| Column | Purpose |
|---|---|
| Surrogate key | Unique key for each historical version; usually generated by the database |
| Business key | Identifies the real-world source record across versions; here, likely `id` from SSOT |
| Tracked attributes | The fields whose changes should create a new version, such as name or product/program IDs |
| Effective start date | When this version becomes valid |
| Effective end date | When this version stops being valid; often an agreed “far future” value marks the current row |
| Current/active flag | Makes it easy to identify the current version |
| Optional audit fields | Load time, source, job ID, created/updated information; useful operationally but not the core SCD2 logic |

For this table, the DDL names these as `cr_prgrm_prdct_ky` (surrogate key), `id` (source ID), `eff_strt_dt`, `eff_end_dt`, and `is_actv`. Other fields such as `etl_dt`, `etl_src_id`, and `etl_job_id` are load metadata, not the business validity history. The DDL is near the end of the `sample SQL file`.

## 3. What “auto increment” means here

The DDL defines:

```sql
cr_prgrm_prdct_ky bigint NOT NULL
  GENERATED ALWAYS AS IDENTITY (START WITH 1 INCREMENT BY 1)
```

This means the database automatically generates a number for `cr_prgrm_prdct_ky` when a row is inserted: 1, 2, 3, and so on. It is the row’s **surrogate primary key**—not the source record’s ID.

The insert query supplies `id`, but does **not** supply `cr_prgrm_prdct_ky`. That omission is intentional: the database generates the surrogate key. With SCD2, a changed record gets a new row and therefore a new surrogate key, while its source/business `id` is repeated across versions.

## 4. How this sample is intended to run

### Step A: Register that a job started

The first control-table MERGE writes a row to `etl_control.control_table` with fields such as:

- `job_id`: job identifier
- `tbl_nm`: target table name
- `ppln_nm`: pipeline name
- `schm_nm`: target schema
- `src_system`: source-system label (`LSC` here)
- `sts`: job status, such as `Started` or `Success`
- `lst_run_ts`: timestamp used as a run/watermark reference
- `merge_qery`, `insert_query`, `ddl_query`: saved SQL text

The control table is operational tracking; it is not the SCD2 dimension itself. The start statement is in the `control-table section`.

### Step B: Prepare the source rows

The source query reads `ssot__careprogramproduct__dlm` and gives source columns shorter target aliases, for example:

- `ssot__Id__c` → `id`
- `ssot__CareProgramId__c` → `cr_prgrm_id`
- `ssot__ProductId__c` → `prdct_id`
- `ssot__Name__c` → `nm`

It also casts or formats dates and adds ETL metadata such as `etl_src_id`, `etl_dt`, `eff_strt_dt`, `eff_end_dt`, and `etl_job_id`.

`ROW_NUMBER() ... PARTITION BY ssot__Id__c ...` ranks multiple source rows for the same ID by `Last_Modified_Date__c`. Filtering to `RN = 1` keeps the latest-ranked row per source ID. If two rows tie on that timestamp, however, which one ranks first may not be deterministic.

The `Last_Modified_Date__c` filter uses the most recent successful control-table timestamp minus 60 minutes. That overlap can help catch late-arriving or delayed source changes, but it does not by itself guarantee that every source change is captured.

### Step C: Match a source record to its current target version

The main MERGE matches on:

```sql
tgt.id <=> src.id
AND tgt.is_actv = TRUE
```

Here, `id` is the business/source key used to find the current version. `<=>` is a null-safe equality operator in dialects such as Spark/Databricks SQL: unlike ordinary `=`, it treats two NULLs as equal. An `id` should normally be non-null for this dimension, so verify that assumption.

The aliases are just shorthand: `tgt` means target table; `src` means prepared source data.

### Step D: Detect changes and expire the old version

The `WHEN MATCHED AND (...)` clause compares tracked source attributes, such as `cr_prgrm_id`, `prdct_id`, and `nm`.

If the source matches an active target row but one of those attributes differs, the update sets:

- `eff_end_dt` to the current date
- `is_actv` to `FALSE`
- `lst_updt_ts` and update metadata

That **closes** the old version; it does not replace its historical values.

### Step E: Insert rows

The MERGE’s `WHEN NOT MATCHED BY TARGET THEN INSERT` handles source IDs that have **no active target row**—typically new records. It inserts the source/business `id` and other values while leaving the identity surrogate key out so the database generates it.

But a changed row **did match** the active target in Step D. A single MERGE update does not also insert the next version for that same match. That is why the file has a separate `INSERT QUERY`: it is intended to insert a new active version for rows closed during the run. Its `opn_flg = 'U'` differs from the initial insert’s `'I'`, apparently to distinguish an update-driven version from an initial insert; confirm what your downstream process expects these codes to mean.

### Step F: Mark the job successful

The final control-table MERGE sets the job status to `Success`, records an end time, and stores the SQL text. See the `success-update section`.

## 6. Important checks before using this sample

- **The job IDs do not consistently match.** The first MERGE uses `141696125945998`, while the control-table row uses `205221172454520`. A later version uses `205221172454520`. Align the job ID throughout so the target metadata and run tracking refer to the same job.
- **The control-table start logic may not start later runs.** Its matched-row update is conditional on the existing status already being `Started`. If the existing row is `Success`, the start statement appears to do nothing; the stored run timestamp may then remain stale. Review the upsert so each new run records its start and watermark.
- **SCD2 end-date semantics need a decision.** The sample expires an old row on `CURRENT_DATE()` and also starts a new version on `CURRENT_DATE()`. If both date endpoints are treated as inclusive, the versions overlap for that date. Define whether the end date is exclusive or set it to the day before the next start.
- **The 60-minute overlap and timestamp logic should be tested.** In particular, check how the success update maintains `lst_run_ts`, and ensure the source filter uses the intended successful run’s timestamp.
- **Null handling deserves care.** Comparing values via `COALESCE(column, '')` or a sentinel date can make NULL equivalent to a real empty string or sentinel value. Use a comparison appropriate to the SQL engine and data types.
- **Source deletions are not visibly handled.** The sample covers new and changed records, but you should decide whether a source record that disappears should expire its active target row.
- **The file contains duplicate/alternative query versions.** Don’t execute every MERGE and INSERT block without first identifying which statements form the intended run sequence.

In short: the intended SCD2 pattern is **find the current row by business key → compare tracked attributes → expire it if changed → insert the new version → record run success**. The generated `cr_prgrm_prdct_ky` gives every version its own row key; the source `id` ties those versions back to the same source record.
